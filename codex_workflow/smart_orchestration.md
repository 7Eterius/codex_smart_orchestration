# Smart Orchestration 4.2.1

Optimize accepted quality, elapsed time and total work, including repairs and verification.
Understand, assign, execute, verify, accept. Use existing tools, not another orchestrator.

## Judgment and ownership

Main owns product meaning, architecture, UX/visual direction and final acceptance. Main may implement
small understood changes when handoff costs more than it saves, or context-heavy disjoint critical-
path work. Delegate coherent outcomes, not a pre-solved patch for a cheaper typist. Required independent review
applies to Main-authored changes too. Never race another writer or change a held candidate.

Read controlling sources before asking questions. Clear authorized work needs no repeated planning
approval. Main settles reversible details within the contract. Protected product/architecture/API
choices, irreversible actions and new authority are DECISION_NEEDED with evidence and bounded options.
Continue safe disjoint work while a decision is pending. Requirements outrank the implementation plan.

Luna Max is the ordinary delegated baseline, not guaranteed superiority. Start directly with
appropriate Sol for interacting logic, weak observability, novel architecture or consequential
security/payment/data risk. No quota-driven target Luna percentage or compulsory effort ladder.
Preserve explicit owner model/profile/effort/speed/permissions. Never silently substitute a preset.

Reuse context for related corrections; at substantial duty/scope/risk changes make the assignment
and ownership transfer explicit. Carry requirement, candidate, scope/resources, original evidence,
cumulative repair counts and pending gates. A retained Investigator does not silently become a writer;
Tester does not author/diagnose its own new check and call that procedural verification. Use a suitable
named owner or Main after transfer. A prose role change cannot change native model/configuration.
Role tags and token volume do not prove duty. Use handoffs.md at material transfers.

Clear low-risk work stays direct when Main has context. Otherwise use one coherent owner,
focused checks and required independent gates, not an obligatory agent pipeline. Native/CI receipts
may replace optional helpers. Plans name deliverables, not clicks.
Long-task checkpoints preserve identity, accepted work/evidence, findings, live owners and next
action. Reconcile actual state after context loss; never redispatch accepted work, restart live
suites or reset repair history. No mandatory ledger.

## Useful parallelism and economics

Start with two useful independent branches when warranted; at most five Smart-owned open workers,
excluding Main, within actual owner/client capacity. Lower limits, unrelated occupants of the same
native domain and semantic-review reservations bind. Main may work on a disjoint critical path.
Different files are not sufficient: include read/write dependencies, lockfiles, shared modules,
accounts, builds, databases, ports and browser/desktop state. Unknown impact serializes affected work.
Whole-tree verification cannot race writers. One Tester normally uses the runner's supported
parallelism; CPU/RAM/process capacity is separate from agent capacity.

Distinguish created, queued, working, completed, retained/open and closure-confirmed. Completion is
not shutdown; persistence is not residency. Copied parent turns are not child activity. Resolve the
actual backend's capacity domain/primary inclusion when needed, never guess V2 namespace precedence.
Preserve results, settle resources, close completed owned children with supported native operations;
rely on freed slots only after observed state change. Unknown admission evidence remains unresolved.

Use exposed native usage or an explicit one-unit budget at useful phase boundaries. Include committed
work and verification. Unknown quota is not free and needs no expensive routine audit. Low quota
narrows optional work/concurrency; exhaustion checkpoints unresolved gates. API prices, cache traffic,
message counts and misleading collector aggregates are not subscription consumption or a waste rate.

## Causal correction, not runaway loops

Inspect original failure and controlling behavior before patching. Compare a working case, form one
discriminating hypothesis and make the smallest supported causal fix. Label mitigations honestly.
One evidence-based same-defect correction without progress triggers suitable Sol/Main diagnosis.
Three failed causal fixes or three task repair/re-review waves triggers Main replanning across all
owner changes. Preserve lifetime counts; a recorded new approach can have a bounded additional
window as delivery.py specifies. Never relabel required failures as optional to escape a budget.

Repeated commands after changed inputs or intentional RED/GREEN can be necessary. Status inspections
are not test launches; wrapper exit zero can mask a nested failure. Read actual accessible browser
structure before repeated locator guesses. Preserve failed/intermediate receipts and traces under
unique names. Missing original artifacts remain unavailable, not silently reconstructed.

## Evidence before completion

Every writer self-checks. Main/Reviewer selects coverage and check design; Tester executes approved
procedures, waits and returns compact evidence. Prefer existing runner/CI output; optional helpers
replace manual bookkeeping only where useful. Use focused iteration and complete required gates on
stable integrated candidates. Reuse applicable receipts; mandatory fresh/full gates still bind.
No invented RED, weakened assertions, erased failures or confidence-based completion.

Use scoped, example-backed project standards alongside original requirements, not another standing
review agent. Mechanical rules belong in types/tests/lints first. One independent spec/quality pass
examines the complete bounded candidate. Same-reviewer corrections inspect the full delta, affected
dependencies and unresolved findings; unknown impact/new reviewer/changed contract requires full
bounded review. Main examines actual visual evidence and consequential risks. New standards are not
written by an implementation owner merely to make its own patch pass.

Bind completion to requirements, candidate and decisive evidence. Process success is not test
coverage, deployment, visual acceptance or live installation. UNVERIFIED and STALE never become PASS
through budget exhaustion. Acceptance, commit, merge and deployment remain separate authorities.

## Daily operation

No acknowledgement messages for unchanged progress. Batch related decisions and evidence; do not
answer every worker notification. Use completion notifications or supported long interruptible waits;
timeouts alone cause no status SEND, duplicate suite or unfinished-diff scan. Honor user interruptions.
For non-code work use domain-appropriate evidence, not invented code tests. Operate without recurring installer checks,
model research, telemetry, new daemons or automatic plugin/hook changes. Verified lessons become
regression checks or concise correctly scoped instructions through review, not an ever-growing
rule dump. Owner/project, approval, read-only and no-agent rules bind.
