# v2.0.0: bounded coordination without routine overhead

## Decision

Keep Normal as the default. Add one optional `chunk_lead` role for authorized,
qualified multi-chunk work, rather than making every task traverse a permanent
Planner/Coordinator/Orchestrator/Implementer/Validator hierarchy.

The goal is lower total cost through accepted outcomes: all parent and worker calls,
reasoning, tools, retries, review, integration and rework. A cheaper first attempt,
lower calls/hour or a higher cache-hit percentage is not enough on its own.

## Adopted improvements

- Fresh Luna xhigh leads own coherent chunk review/correction/local acceptance;
  Sol main retains product, design, architecture and final milestone judgment.
- Event-driven completion and blocker communication replaces progress polling and
  acknowledgement exchanges. Same-chunk repairs reuse context; fresh chunks do not.
- Independent verification holds candidate inputs and target steady, preserves original
  failures, and invalidates affected evidence when relevant inputs change.
- Main verifies candidate/evidence and high-risk exceptions instead of mechanically
  duplicating a qualified lead's complete local review.
- Browser operation stays cheap: use sufficient structured tools, bounded deterministic
  batches, target/account checks, reusable sessions and useful screenshots only.
  An easy GUI action does not remove security, billing or production risk.
- An optional scoped fingerprint helper makes file identity checks deterministic.
  It never converts matching hashes into behavioral acceptance.
- Core policy stays under 1,200 words; coordinated and browser details load on demand.
  Leaf/lead TOML instructions stay under 200 words each. These are maintenance budgets,
  not proof of lower inference cost.
- Installation now protects current managed runtime edits and avoids broad retirement
  of marked skill directories or historical source caches. Disk integrity is checked
  separately from live model/delegation behavior.

## Deliberately not adopted

No compulsory coordinator for small tasks, unlimited recursive agents, new telemetry
service, duplicate project ledger, fixed worktree/disk quota regime, automatic cap
increase, guessed `max_depth` key, automatic Astra/Max promotion, approval weakening or
routine release machinery. Code-level batch execution is used only when the active
runtime exposes it and per-action failures/authority remain inspectable.

We do not turn an API feature into a claim that a Codex configuration file supports
it. In-session effort changes, deferred tool loading, asynchronous calls and nested
agent behavior must follow the actual client/backend interfaces and restrictions.

## Research and applicability

Reviewed 2026-09-24. Links are reference material, not instructions loaded into every task.

### OpenAI subagents and configuration

[Subagents](https://developers.openai.com/codex/subagents) documents custom agent files,
model/effort selection, `agents.enabled`, inherited session settings and a spawned-thread
cap excluding primary. It recommends narrow agents and warns that subagent workflows
can consume more tokens. This supports Normal by default, a single bounded lead and
preservation of existing limits. It does not establish that this package's exact nested
arrangement, tools or reclamation work in every installed client.

### Prompt caching and selective context

[Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) favors
stable prefixes and appending changing inputs. It describes GPT-6 API configuration
updates and cache-aware deferred tools. Smart applies the stable-context principle,
but does not invent a Codex self-switching configuration mechanism.

[Codex best practices](https://developers.openai.com/codex/learn/best-practices) supports
clear goals/constraints/done criteria, practical short instructions, relevant context,
verification and controlled permissions. Optional guides avoid making normal work
carry long coordination rules.

### Deterministic batches and GUI work

[Programmatic tool calling](https://developers.openai.com/api/docs/guides/tools-programmatic-tool-calling)
recommends code for predictable filtering/joining/validation and direct calls for
single actions, adaptive judgment and approval-sensitive work. Smart copies this
selection principle, not a dependency on the Responses API or a new hosted tool.

[Computer Use](https://learn.chatgpt.com/docs/computer-use) distinguishes GUI-dependent
tasks from those served by structured integrations, recommends the built-in browser
for local web apps and emphasizes app/OS permission boundaries. Strong visual reasoning
and routine navigation are therefore separate jobs in Smart.

### Arcana and the community observation

[Arcana coordinated-workflow preview](https://github.com/dayowe/arcana-codex-plugins/tree/experiment/coordinated-staged-workflow)
separates long-lived scheduling from bounded detailed review. Its experimental
`0.2.0-alpha.5` README explicitly distinguishes structural validation from live
qualification and measured savings. Smart uses original, substantially smaller
instructions rather than importing the five large skills and execution framework.

[The author's Reddit report](https://www.reddit.com/r/codex/comments/1wo58e3/45_less_token_burn_after_reworking_my_codex/)
reported lower raw tokens/hour and fewer long-lived coordinator calls after changing
workflow structure. Those before/after observations are not a controlled benchmark
for Smart, a guaranteed 45% reduction, or Codex subscription accounting. Smart's
qualification therefore compares representative accepted work, including added lead
cost and correction overhead, instead of promising a universal percentage.

## What is and is not established

The automated suite establishes the package's written/configuration contracts,
installer behavior, migration/rollback and bounded candidate helper behavior. It does
not run GPT-6 workers, control the user's computer, prove nested Codex delegation,
measure UI/UX quality or establish token savings.

The bundled [live trial](../codex_workflow/qualification.md) is the admission check for
consequential coordinated work. Reuse an applicable qualification; repeat only affected
mechanics after client/configuration/model changes. Until it passes, use Normal and
report the limitation, or hold an explicitly coordinated-only request.
