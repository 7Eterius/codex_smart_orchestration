# Smart Orchestration 3.1.0

## Design decision

Use Luna Max for coherent ordinary work, Sol Low for bounded stronger-family problem-solving,
Sol Medium for deep interacting logic and Sol High for serious or critical work. Keep Main's
judgment, direct small-task path and disjoint critical-path execution. Add no manager layer.

The existing tester name now means procedural Luna Medium execution. New Reviewer/Luna Max and
Senior Reviewer/Sol High carry independent semantic review. New Deep Executor/Sol Medium makes
all three selected Sol levels concrete presets. Routine returns to ordinary coding; Default is
the Sol Low middle lane. Companion/Archivist also use Luna Max; batch them rather than creating
expensive handoffs for tiny reads. These are on-demand roles, not eleven concurrent agents.

The allocator recommends those routes from supplied task facts. It preserves the legacy six-field
input, adds optional difficulty and kind=testing, and keeps kind=verification semantic. Critical
risk cannot be downgraded by an ordinary difficulty label; deep=true cannot be weakened by it.
Actual native model/effort availability remains a runtime qualification obligation.

## Testing and concurrency

Tester owns approved processes and compact evidence receipts. Focused checks during edits and
complete required suites on stable integrated candidates avoid unnecessary reruns. Main and
Reviewer reuse applicable evidence; mandatory fresh/full gates, discovery, expected shards,
coverage and failure visibility remain binding. No zero-test green, hidden flaky reruns, weakened
assertions, production fixes or semantic sign-off by procedural Tester. Runner parallelism needs
its own CPU/RAM/resource budget; five agent slots do not imply five full suites.

The policy ceiling becomes five owned open worker threads, excluding Main. Lower configured caps
are preserved. Candidate holds and stopped-writer/resource checks cover both testing and review,
but only semantic reviewers can consume the shared review reservation. Test receipts cannot
replace independent judgment. Scope downgrade, held-candidate, native-release and reservation
regressions from 3.0.1 remain active. Main may work only on a genuinely disjoint critical path.

## Evidence reviewed, 5 October 2026

The two requested firsthand discussion threads contain both successful Luna Max coding reports
and accounts of drift, incomplete work and slow runs. They are useful failure examples, not a
controlled comparison of task difficulty, effort, harness, token use or accepted quality:
[thread one](https://www.reddit.com/r/codex/comments/1wox48m/luna_6_vs_luna_56/) and
[thread two](https://www.reddit.com/r/codex/comments/1wojc0q/so_what_about_gpt6_luna_xhigh/).

OpenAI reports Luna Max at 66.6% on DeepSWE 1.1 in its own evaluation. That supports trying Max
for substantial coding, not a guarantee for this repository or every kind of bug.
[GPT-6 Sol and Luna announcement](https://openai.com/index/introducing-gpt-6-sol-and-luna/).

GPT-6.1 Sol was announced on 29 September 2026. The announcement describes stronger coding
results and efficiency than the prior Sol generation. It does not establish a universal
Sol Low versus Luna Max crossover for this workflow.
[GPT-6.1 Sol announcement](https://openai.com/index/introducing-gpt-6-1-sol/).

The Luna model documentation exposes low, medium, high, xhigh and max effort, among supported
settings. Standard API input/output prices are $0.10/$0.50 per million tokens; Sol 6.1's
announcement lists $2/$10. Those are token rates, not cost per accepted task or a Codex
subscription quota formula. Cached inputs and reasoning/output volumes matter.
[Luna model reference](https://developers.openai.com/api/docs/models/gpt-6-luna).

Official reasoning guidance treats effort as a speed/quality/token-budget tradeoff. Choosing
Sol Low as a middle lane is a workflow hypothesis to evaluate, not evidence that it always
beats Luna Max. Higher effort need not be the fastest or cheapest end-to-end choice.
[Reasoning guidance](https://developers.openai.com/api/docs/guides/reasoning).

The Codex configuration reference documents the spawned-thread cap excluding the primary thread,
its legacy alias and role/default model settings. Disk configuration still does not prove live
selection, nesting support, isolation or available capacity.
[Codex configuration reference](https://developers.openai.com/codex/config-reference/).

## Installation and validation

Version is 3.1.0. Preserve owner configuration, permissions, speed, Main/profile/Plan effort,
project files and backups. Fresh child defaults are Luna Max and five threads. Existing lower
caps remain lower until deliberately changed. Restart manually and use fresh conversations so
old Tester-as-reviewer context is not mixed with new role semantics. No automatic native restart.

Run the current suite, syntax checks and exact migration/rollback tests, including 3.0.1, before
publication. The existing CI matrix and immutable-source release gate are retained. Archived
2.7.1 tests remain historical reference rather than a substitute for current validation.
Passing CI means source/helper/installation contracts passed, not measured model capability.

## How to evaluate the change

Compare representative ordinary, moderate, deep, review and test-heavy tasks against 3.0.1 under
similar contexts and acceptance criteria. Record first-pass acceptance, elapsed time, repair
rounds, total input/cached/output/reasoning use when exposed, actual quota delta, and duplicate
suite count. Keep quality and mandatory gates fixed. Attribute machine test time separately
from model/tool orchestration time. Retain cases where Sol-first wins as well as Luna wins.

No percentage saving, latency improvement, native-compliance guarantee or universal best effort
setting is claimed without those measurements.
