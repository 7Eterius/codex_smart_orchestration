# v1.8.0: runtime-aware GPT-6 orchestration

v1.8.0 keeps the eight-role GPT-6 worker map from v1.7.0 and changes how Smart uses
it. The target is accepted quality per token, not latency. Luna remains the bounded
workhorse; Sol stays focused on parent judgment and rare advisory escalation.

## Primary implementation lane

Routine Luna High is now explicitly the normal implementation lane, including
ordinary multi-file work when contracts are settled. `default_executor` keeps Luna
Max, but it is a deep-work exception for genuinely tangled bounded implementation,
long-horizon cross-module debugging, or work that remains difficult after bounded
High-effort work.

This avoids adding another always-visible agent role just to represent another effort
rung. The model registry stays small and Max is consumed by routing policy rather than
by making it the reflexive destination for anything nontrivial.

## Parent effort

The installer still preserves the owner's parent model and effort byte-for-byte.
For owners who choose GPT-6 Sol manually, Smart documents Medium as the normal
cost/quality baseline. Higher effort is reserved for a named hard judgment.

GPT-6 can change reasoning effort inside a session while preserving the earlier
cached prefix in supported APIs. Smart uses that only when the active runtime exposes
a safe in-session mechanism. It does not invent Codex TOML keys or pretend to change
its own effort.

## Evidence-grounded cheap workers

Companion, Investigator and Archivist now have a stronger evidence contract:

- factual claims point to an exact source, path or symbol when available;
- inference is labeled as inference;
- missing evidence remains unknown rather than being reconstructed from plausibility.

This is especially important for permanent project memory and external research,
where a cheap but plausible synthesis error can outlive the task that created it.

## Tool and context economy

Smart now prefers progressive disclosure and stable prefixes. Follow-ups reuse the
same worker and send deltas instead of repeating unchanged context. Long logs stay in
artifacts.

When the runtime exposes deferred tool loading or tool search, irrelevant schemas
stay deferred and only the needed namespace is discovered. Smart does not add
unverified configuration keys to force that behavior.

When async tool calls are exposed, they can overlap slow I/O without creating an
extra waiting agent. In multi-agent mode Smart follows the GPT-6 restriction against
combining async tools with parallel tool calls.

## Browser and Computer Use

Computer Use is now an explicit verification lane instead of a generic reason to
spawn more agents or raise model effort.

For local web work, source/tests plus browser DOM, console and network evidence come
before repeated screenshot-only diagnosis. The built-in browser is preferred for
normal local web verification. Computer Use is reserved for native or GUI-only
behavior, simulators, system settings and multi-app journeys.

GUI verification is batched around a stable candidate. The main still owns final
visual/product acceptance and directly reviews required screenshots. GPT-6 Astra is
not automatic. It is an owner-selected escalation for difficult screenshot or
spatial visual judgment where the added capability is worth its much higher Codex
credit rate.

## What is intentionally unchanged

The named role map remains:

- Simple Luna Low
- Routine Luna High
- Default Luna Max
- Senior Sol xhigh
- Tester Luna xhigh
- Companion Luna Medium
- Investigator Luna xhigh
- Archivist Luna Medium

There is no automatic parent-model rewrite, no new token-reporting skill, no automatic
Astra escalation, no per-project Smart install, and no weaker repository verification
gate.
