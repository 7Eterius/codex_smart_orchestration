# v1.6.0: GPT-6 Luna/Sol worker routing

## Why a minor-version bump

Every named Smart Orchestration worker moves from GPT-5.6 to GPT-6, and several
reasoning-effort tiers change. The parent model remains owner-selected and is not
rewritten by the installer. This is therefore v1.6.0 rather than a v1.5 patch.

## Evidence used

As of 2026-09-22, OpenAI documents GPT-6 Luna as its most efficient model for
focused, high-volume tasks and GPT-6 Sol as built for complex coding and agentic
workflows. Both expose a 1,050,000-token context window and the current reasoning
ladder. Standard API short-context pricing is $0.10/$0.01/$0.50 per million
Luna input/cached/output tokens and $2.00/$0.20/$10.00 for Sol.

Compared with the published GPT-5.6 Luna prices, GPT-6 Luna input and cached input
are 50% lower and output is about 58.3% lower. GPT-6 Sol is 50% lower than GPT-5.6
Sol for input, cached input and output. GPT-6 Sol still costs 20x GPT-6 Luna per
text token in each of those three categories.

**API pricing is not the included Codex/ChatGPT plan quota.** These ratios are a
routing-economics reference, not a promise about the owner's weekly subscription
allowance. Requests above 272K input tokens also receive full-request price
multipliers, so the existing context-discipline rules remain useful.

## Benchmark status and effort tuning

No public score table for GPT-6 Luna or GPT-6 Sol was found in OpenAI's current
model pages or launch benchmark tables. The current GPT-6 Astra launch table
benchmarks Astra and GPT-5.6 Sol, not the new GPT-6 Luna/Sol tiers. Third-party
reports available immediately after release are sparse and not suitable for
setting quality thresholds.

Therefore effort tuning uses OpenAI's current **model-selection guidance**, not
invented benchmark inheritance from GPT-5.6:

| Role | v1.6.0 | Rationale |
| --- | --- | --- |
| simple_executor | GPT-6 Luna Low | fine-grained, well-scoped edits |
| routine_executor | GPT-6 Luna Medium | clear briefs and coordinated updates |
| default_executor | GPT-6 Luna xhigh | constrained difficult implementation/diagnosis |
| senior_executor | GPT-6 Sol Medium | judgment-heavy coding, research and decisions |
| tester | GPT-6 Luna xhigh | independent verification at bounded cost; material ambiguity escalates |
| companion | GPT-6 Luna Medium | compact targeted context consolidation |
| investigator | GPT-6 Luna xhigh | current-context/evidence discovery and constrained investigation |
| archivist | GPT-6 Luna Medium | concise verified memory and synthesis |

OpenAI explicitly describes Luna Low, Luna Medium, Luna Extra High and Sol Medium
in closely matching workload terms and says the guide is a starting point to be
validated on real workflows. We keep that experimental posture.

Tester stays Luna xhigh rather than automatically moving to Sol xhigh. Thorough
verification can justify stronger reasoning, but the workflow already has parent
acceptance and a Sol escalation path, while Sol's API token reference remains 20x
Luna. There is not yet GPT-6 benchmark evidence showing that every independent
verification should pay that premium.

Default Executor moves from old Luna Max to GPT-6 Luna xhigh. The current guide
places constrained problem-solving at Luna Extra High; Max remains available for
future measured escalation but is not the routine default.

## Main model

The installer intentionally preserves the owner's selected parent model, effort,
Plan-mode effort and speed. For normal quality-first development, GPT-6 Sol Medium
is the documented starting point closest to the main role's everyday coding and
judgment responsibilities. Increase effort only when the task's ambiguity or error
cost warrants it. This recommendation does not auto-edit the parent.

## Upgrade safety

Fresh installs use GPT-6 Luna Medium as the anonymous subagent fallback. Named
roles are the real Smart assignments and always migrate to GPT-6.

An existing explicit `agents.default_subagent_model` is still preserved. Older
Smart versions may have written `gpt-5.6-luna` there, but the current installer
cannot prove whether a matching value was workflow-generated or deliberately
owner-pinned. It warns instead of silently overwriting that boundary. Named worker
roles are unaffected. The owner may update an old explicit fallback deliberately
after reviewing the warning.

No application project, project memory, owner parent setting, permissions, tool
surface, reporting policy or verification gate is changed by the model migration.

## Validation

v1.6.0 adds exact role-map, current price-reference, fresh-install and exact
v1.5.3 upgrade/reapply/rollback tests. All prior suites remain in CI. Tests confirm
configuration and migration behavior, not live model capability or weekly-plan
savings. After adoption, compare accepted tasks including retries, owner-rejected
visuals and required verification before changing efforts again.
