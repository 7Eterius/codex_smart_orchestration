# 2.5.0: GPT-6.1 Sol judgment and less routine supervision

## Scope

Main baseline is GPT-6.1 Sol Medium; the named Senior role is GPT-6.1 Sol xhigh.
Seven Luna roles, their effort, sandbox and delegation settings remain unchanged.
Explicit owner parent/profile/Plan/fallback/permission/capacity settings remain protected.
Choose the new Main baseline explicitly in the client; installation alone does not switch
an existing session. Missing runtime availability remains a limitation, never a silent
fallback to a different model.

## Lessons applied

The usage review supports stronger economical delegation, but request counts and raw-token
shares do not establish code quality or causal savings. Supervision-heavy traces, scarce
named Simple activity, long-lived contexts and uncertain closure attribution identify
inspection targets. No personal logs, task details or account measurements are published here.

2.5 specifies meaningful wake conditions in the main policy, execution guide and activation
bootstrap. Workers own command/test/browser waits and ordinary repair. A wait timeout alone
is not a new task or reason for a progress SEND, repeated inspection or test. Use supported
long interruptible waits or completion events, never invented APIs or rapid polling loops.
Main still performs early design checkpoints, detailed real-result review and reassessment
of delegated corrections. User interruptions and real errors remain actionable.

The two-thread target is now explicitly run-wide, including descendants, support workers
and prior units. This aligns prose with the allocation helper's existing global owned-thread
check. It is not two slots per assignment. Completion is not native closure; preserve
results/resources and observe eligible native release. Do not raise user capacity or close
unrelated work based on a profiler's temporal-overlap estimate.

Accepted milestones gain a clearer context boundary. Reuse the writer for actual corrections;
use a fresh bounded context for a new contract after handoff/release. Preserve setup and
consult current decisions/changed evidence after compaction rather than rediscovering the
whole archive. There is no forced main restart or per-command journal.

## Configuration assessment

The read-only assessment now returns recommended_parent and parent_baseline_status beside
configured_parent. A valid mismatch is a warning, not an automatic rewrite or failed disk
integrity. Known unsupported none/minimal efforts for gpt-6.1-sol are errors requiring an
explicit correction. The assessment neither resolves profile precedence nor proves account
access, per-run selection or client behavior. It never echoes arbitrary profile instructions.

## Validation

Current model/version tests are updated; historical source baselines remain pinned.
Existing delegation, candidate hold, independent review, permissions, path/ownership,
transaction and lifecycle tests remain. New tests cover baseline read-only behavior,
unsupported efforts, global budget across units, communication/design contracts and exact
archived 2.4 -> 2.5 -> no-op reapply -> rollback. Historical tests permit only the authorized
Senior model change while retaining effort/sandbox/permission checks.

These are source, configuration and installation checks, not native enforcement. There is
no measured savings claim. Live tools can still require adaptation. No new manager, mode,
base-prompt override, scheduler, monitoring daemon or mandatory qualification is added.

## Measurement limitations to preserve

Primary reports and already-running carry-in workers must be accounted for separately and
combined once. Inclusive subtrees overlap. Role labels need actual metadata; underscore
incompatibilities in an external audit parser do not prove runtime routing failures.
Missing close events, ambiguous spawn labels and temporal lifetime overlap cannot establish
thread leakage or permission violations. A price-complete token table is not a complete
bill: cache writes, tools, long-context and speed adjustments may still be absent.
