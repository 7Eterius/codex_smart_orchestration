# 2.2.0: one adaptive execution loop

Prepared against main `460ef504779dced6eee771e483d910efea844bee`, September 24, 2026.
This change is delivered as a source upgrade bundle when GitHub write tools are not
available. It is not a claim that the remote repository or a user's installation changed.

## Evidence and inference

The supplied isolated 2.1 trial demonstrated a named Simple read, one nested three-thread
implementation/review loop, independent rejection, a held candidate, same-writer repair,
fresh validation and local acceptance. A second lead spawned, but its first Routine
spawn failed with `agent thread limit reached`. No retry or capacity change was made.
The exact accounting cause, repeated group completion, model/permission metadata and
later recovery mechanics remained unverified. No cost benchmark ran.

The design therefore does not claim that leaked threads were proven to be the cause.
It removes a manager slot and specifies completion versus native closure explicitly.
The trial's PASS/FAIL/UNVERIFIED distinctions remain intact; a revised policy does not
retroactively qualify that client or prove the new owner's delegation configuration.
Private source reports and local paths are not included in this public design record.

## Changes and tradeoffs

1. Remove the Normal/Coordinated choice and dedicated Chunk Lead. One bounded owner
   executes; Tester independently reviews actual diff/contracts and behavior where
   required; main owns consequential judgments and acceptance. This removes routine
   manager overhead but does not establish a measured quality/cost improvement.
2. Permit Routine/Default to dispatch only their independent Tester when explicitly
   authorized and natively supported. Main-dispatched review is the same workflow when
   that optimization is not established. There is no global qualification gate that
   disables direct cheap execution merely because nested turnover failed.
3. Target two open Smart threads per unit, not three required for every repair loop.
   Keep the configured cap and explicit owner choices. Slot scarcity changes scheduling,
   not models or gates. With no safe release/reuse, checkpoint rather than retry blindly.
4. Observe closure, do not infer it from a final message. Preserve evidence and resource
   ownership; close completed direct children before parents. Requesting closure neither
   proves release nor authorizes resource deletion. The pure helper enforces its supplied
   state invariants but cannot call native tools or authenticate observations.
5. Keep simple, reversible established presentation changes from acquiring automatic
   duplicate review solely due to an UI label. Required project gates and material
   security/financial/data/behavior risks retain independent verification.
6. Keep repeated browser procedures and setup reusable. Use deterministic local checks
   when sufficient; reserve high intelligence for ambiguous judgments and failures.
   Do not substitute API-only tests for required real journeys or visuals for persistence.
7. Make installed policy and observed runtime status distinct. Disk status reports
   `execution_policy: adaptive` and `runtime_observation: not_inspected`, not a permanent
   unverified-mode field. Configured model defaults remain distinct from actual runs.

A simpler hierarchy cannot make task classification infallible. The real objective is
more satisfactory accepted work per allowance, including all model layers and repairs.
Do not promise a percentage reduction, five-day usage or a solved client capacity bug.

## Primary references

- [Codex subagents](https://developers.openai.com/codex/subagents): custom-role configuration,
  named model/effort selection, native agent operations and permission inheritance.
- [Codex configuration](https://developers.openai.com/codex/config-reference):
  `agents.max_concurrent_threads_per_session` limits concurrently open spawned threads,
  excluding the primary thread. A configured cap is not a live occupancy observation.
- User-supplied September 24, 2026 isolated mechanics qualification: evidence summarized
  above; source retained privately rather than published in the repository.

## Validation boundary

Allocation tests are pure/synthetic. Source update tests establish pinned-content checks,
no-write preview, controlled changes and rollback behavior. Exact archive migration
regressions require full repository history and must run in the resulting checkout.
Native owner/Tester spawning, actual role metadata, closure and measured economic
outcomes require the actual client and representative accepted work.
