# 3.0.1: reliable parallel allocation and reusable review context

Reviewed 3.0.0 baseline: `474326b0892e473bcde5638bccf81eb8944aac50`.
This patch corrects allocator edge cases before routine adoption. It does not redesign the
workflow or claim that these source defects caused observed real-session failures.

## Reproduced findings

### Scope omission could bypass known conflicts

The 3.0 allocator checked Main and peer access only when the request had a scope. An unscoped
request could therefore be admitted despite an explicitly recorded Main writer, or an active
scoped writer in the same unit. Mixed legacy/scoped records now require the missing request
scope instead of discarding the known concurrency evidence. Fully legacy serial use remains
supported; a reused worker can inherit its already-validated scope.

### Holds were not enforced independently of peer overlap

A stopped writer could be reused with candidate_held=true when no reviewer thread happened
to be present. Conversely, a scoped standalone reviewer could start without an explicit hold
when no peer conflict exposed it. An explicitly held candidate now blocks writer work, and
scoped review requires candidate_held=true. Released same-writer repair and readback remain
available. This is a prospective check of supplied facts, not a filesystem lock.

### Review capacity could be consumed by unrelated work

3.0 treated any existing Tester as occupying the shared future review pool. But an unrelated
retained Tester cannot be reused for a different unit under the same allocator's ownership
rules. It could suppress a needed reservation and allow unrelated work to fill the last slot.
An unrelated newly requested Tester could also consume the reserved slot without serving the
pending review. Both cases now preserve real capacity for queued reviews.

A requested reviewer serving the pending queue can consume that shared slot. Two independent
writers and their ready reviewers can still pipeline within actual capacity. A closing or
unknown reviewer is not considered reusable. No slot is reclaimed until native closure is
observed; no unrelated or active thread is automatically closed.

### Reuse discarded newly requested review reservations

The reuse path returned before evaluating reserve=1 and omitted the returned reservation
obligation. Reusing context still costs no new thread, but an explicitly requested new review
reservation now checks available capacity or an existing same-unit reviewer. The returned
record_review_reserved preserves the obligation. An unknown cap blocks a new slot assumption,
not ordinary same-thread reuse without one. Existing serial-review fallback remains available.

## Small efficiency correction

Equivalent scope lists in a different order used to trigger scope_change_requires_transfer.
Validated read/write/resource path lists are sets for ownership comparison. Reordering the
same entries now reuses the worker context; real additions, removals or workspace changes
still require an explicit transfer. Duplicate and ambiguous paths remain invalid.

The allocator shares its capacity check rather than maintaining inconsistent spawn/reuse
rules. No source scan, network call, model call, state service or new schema field is added.

## Preserved 3.0 architecture

Main may finish small understood tasks and own a context-heavy critical path. Main retains
product, architecture, design and final acceptance. Default, Tester and Investigator remain
GPT-6.1 Sol Medium; Senior remains Sol xhigh. Luna remains for known mechanical recipes,
prescribed transformations, exact lookup and authorized checkpoint memory.

Routing, all eight role files, the activation bootstrap, model/effort/permission settings and
four-thread ceiling are unchanged. The on-demand execution guide documents the corrected
protocol within its existing prompt budget. Required verification, Main-authored independent
review, actual visual assessment and same-reviewer correction-delta checks remain intact.
No new manager, mode, permanent ledger, per-click ceremony or mandatory extra review is added.

The original 3.0 design and review are preserved in the
[3.0.0 source notes](https://github.com/7Eterius/codex_smart_orchestration/blob/474326b0892e473bcde5638bccf81eb8944aac50/docs/v3.0.md).

## Validation

The new regression suite exercises real allocator entry points and CLI exit codes, positive
parallel/reuse cases, nonmutation, hold/release transitions, capacity preservation and exact
archived-3.0 reproductions of six formerly admitted unsafe or unschedulable plans. Existing
routing, candidate, evidence, configuration, installation and release suites remain unchanged
except the current version expectation and an added 3.0 migration baseline.

Historical upgrade tests now include nine archived baselines, including exact 3.0.0 -> 3.0.1
-> no-op reapply -> byte-for-byte rollback, preserving owner configuration and project files.
The unchanged 309-test 2.7.1 suite remains a separate historical reference, not evidence that
current code passed those tests. Full Git history is required in CI; missing local history
is not reported as a pass.

Source tests cannot prove native tool compliance, authentic scope observations, absence of
all defects, faster real tasks or reduced subscription consumption. The helper cannot detect
an undeclared dependency, falsely reported hold, incorrect alias or invented authority.
These corrections reduce avoidable scheduling mistakes; live performance still needs actual use.

## Installation

Use the existing pinned-main preview/apply/check procedure, manually restart Codex and begin
a fresh conversation. Existing explicit capacities, Main/profile selections, generic child
fallbacks, speed and permissions remain unchanged. An older cap of two or three is reported,
not silently raised. No local client is changed merely by publishing this patch.
