# 2.6.0: progressive context, deterministic challenge and falsification-first review

## Why

Smart 2.5 moved substantial implementation to economical workers and reduced routine Main
supervision. 2.6 borrows a small set of ideas from
[Kiborgik/BlaBla](https://github.com/Kiborgik/blabla): progressive disclosure, evidence
ordering, deterministic contradiction checks, explicit uncertainty handoff and
falsification-first review. Smart does not adopt BlaBla's DSL, persistent task state,
mandatory task ceremony or universal independent-review policy.

The goal is narrower: catch cheap, objective handoff problems before they consume Main or
Tester attention, while keeping GPT-6.1 Sol focused on product, architecture, design and
acceptance judgment.

## Changes

### Progressive disclosure

Workers start from project instructions or a status/index/architecture surface, open the
relevant system/contract/design identity, then retrieve only the specific rule/file/evidence
needed. Projects with their own queryable status/explain/index mechanism should use it;
projects without one continue using bounded search/read. This is a context-economy rule,
not a new Smart project-memory format.

### Deterministic challenge helper

`runtime/challenge.py` is a new read-only, no-network, no-model helper. Given one small
structured record, it returns CLEAR or one grounded contradiction covering scope/attribution
conflicts, unresolved DECISION_NEEDED, required missing/unchanged deliverables, unresolved
blocking findings, required failed/blocked/unrun/deferred/not-applicable/STALE/UNVERIFIED
evidence, or reused evidence where a fresh gate is required.

It never scans chat/source on its own, authenticates observations, decides semantic
correctness, grants authority or replaces independent review. CLEAR means only that none
of its supported contradictions exists in supplied facts. Smart does not create persistent
task state merely to feed it.

### Evidence precedence and staleness

Worker narratives are explicitly advisory. Actual repository/target state, deterministic
readback and current executed checks outrank summaries. STALE and UNVERIFIED are named states.
Candidate/contract/target drift invalidates affected prior evidence; missing proof stays unknown.

### DECISION_NEEDED

Workers keep ordinary implementation choices. A choice that would alter product meaning,
architecture, UX/visual direction, contract semantics, scope or authority returns a compact
DECISION_NEEDED handoff: question, bounded options when useful, evidence, why the choice lies
outside the settled brief, and an optional provisional pick. Smart deliberately does not use
numeric confidence thresholds. Main answers only the protected decision and sends the delta
back to the same worker.

### Falsification-first Tester

Tester starts from the original task and complete diff, accounts for every deliverable,
reads controlling code before asserting semantic defects, inspects sibling cases around
changed branches and seeks the smallest concrete counterexample. BLOCKING is reserved for
wrong, incomplete or untrue work; style/optional cleanup is NON-BLOCKING. Tester never edits
the candidate.

## Preserved architecture

There are still eight roles, one adaptive loop and no manager/Chunk Lead. Main remains
GPT-6.1 Sol Medium as recommended baseline; Senior remains GPT-6.1 Sol xhigh; all Luna role
models/efforts are unchanged. The run-wide two-thread target, native-release rules, candidate
holds, design review, owner settings, permissions and rollback behavior remain.

The challenge helper is progressive enhancement. Low-risk work without existing structured
facts does not need a new ledger. Existing `candidate.py`, `boundary.py` and
`allocation.py` remain bounded advisory helpers rather than native enforcement.

## Validation scope

Tests cover challenge ordering/fail-closed parsing, progressive-disclosure and evidence-state
contracts, DECISION_NEEDED handoffs, falsification-first Tester instructions, helper
installation/fingerprinting and exact archived 2.5 -> 2.6 -> no-op reapply -> rollback.
Historical source/migration tests remain.

These tests do not establish live Codex compliance, semantic correctness, project-memory
quality or measured savings. BlaBla's published research shows useful executable feedback
but does not establish a general efficiency or final-drift advantage; Smart therefore
borrows mechanisms rather than adopting the framework wholesale.
